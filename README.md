# 电商客服大模型微调项目

基于 Qwen2.5-1.5B-Instruct，针对电商客服场景完成 **QLoRA 微调** 与 **DPO 偏好对齐**，并在过程中发现并修复了数据泄漏、回复幻觉、评测方法学等一系列工程问题。

> 关联仓库：LLM 高并发推理服务 & 性能压测平台 —— 同一模型的工程化部署与性能归因。
> 本仓库关注**模型能力**（学会回答、对齐回复质量），压测仓库关注**工程能力**（高并发服务化 + 性能评测）。

## 技术路线

数据构建（零泄漏） → SFT 微调（QLoRA） → DPO 对齐 → 定向 DPO 修复幻觉 → 推理部署 → 性能评测

## 环境

- GPU: NVIDIA RTX 4060Ti (8GB)
- 框架: Unsloth + TRL + Transformers
- 模型: Qwen2.5-1.5B-Instruct

## 数据

自构建电商客服合成数据集，覆盖 5 类意图（物流查询 / 退换货 / 商品咨询 / 投诉建议 / 售后问题）。数据采用**模板 + 槽位填充**生成，并针对常见陷阱做了专门设计：

- **零泄漏切分**：按去重后的唯一问题切分训练/测试集，并用 `assert` 自检，保证测试集与训练集无任何重合。
- **订单号条件性出现**：约 1/3 样本设为"用户未提供订单号"，对应答案只能礼貌索要、不得复述或编造订单号；其余样本才在答案中复述真实订单号。这是为根治"幻觉订单号"专门设计的。
- 规模：SFT 训练集约 1970 条、测试集约 220 条（全部唯一）；DPO 偏好数据共 168 条（基础 120 条 + 反幻觉定向 48 条）。

> 数据局限：仍为模板合成，多样性有上限，不能代表真实用户的口语化/长尾问法。真实泛化需引入真实客服对话，见「已知局限」。

## 训练配置

| 阶段 | 方法 | 参数 |
|------|------|------|
| SFT  | QLoRA（4bit NF4 基座 + LoRA adapter） | rank=16, alpha=32, epoch=3, 每 epoch 存档 |
| DPO  | 偏好对齐（QLoRA） | beta=0.1, epoch=2, gradient_accumulation=2 |

LoRA 可训练参数：约 18.4M / 1562M = **1.18%**（基座 4bit 加载并冻结，仅训练 adapter）。

## 工程过程中发现并修复的关键问题

这部分记录排障过程，是本项目的核心价值——很多问题在合成数据微调中很常见，但只看训练集指标会被掩盖。

**1. 训练/测试集 100% 泄漏（最严重）**
初版数据生成是「先重复采样再切分」：仅 15 个唯一模板被有放回抽样到 2000 条、每个重复约 120 次，切分后测试集的全部唯一内容都已出现在训练集中。后果是 SFT loss 能降到 0.0x、DPO 在偏好集上"100% accuracies"——这些都只是**背诵指标**，不代表任何泛化能力。
修复：按唯一样本去重后再切分 + 槽位填充扩充多样性 + 零泄漏自检。

**2. 回复幻觉订单号 / 语义串味**
对未提供订单号的短问（如"我要申请退款"），模型会凭空编造订单号，甚至串味成物流催发货。
排查：先尝试调整 SFT 中无订单号样本的比例（8% → 14% → 34%），改善有限——说明这是 SFT「模仿」难以纠正的。最终改用**定向 DPO**：构造同一短问下 chosen（索要订单号）vs rejected（编造订单号）的偏好对，让梯度直接惩罚该行为。**贪心解码下"编造订单号"这一具体失败模式基本消除**。
但需如实指出：DPO 在压住该问题的同时引入了新的不可靠行为（虚构系统能力、回复啰嗦），独立评测显示其整体质量**未超过 SFT**（见「实验结果」）。即"局部修复有效，但整体净效果为负"——这正是用评测做判断的价值所在。

**3. 评测方法学缺陷**
原性能脚本存在三个问题：采样解码导致结果不可复现；用 8 个样本计算 P90（实际取到的是最大值）；GPU 异步执行未同步计时，出现过负延迟。
修复：贪心解码、充分预热并丢弃冷启动样本、`torch.cuda.synchronize()` 前后同步、线性插值正确计算百分位、样本不足时拒绝输出 P90/P99。

**4. 训练/推理格式一致性**
统一 system prompt 与 chat template（`apply_chat_template`），保证 SFT、DPO、serve 三处格式逐字一致，避免训练-推理错配压低真实表现。

## 实验结果

> 方法：在独立测试集（同分布 template 桶）+ 手写非模板探针（hard 桶）上，对 base / SFT / SFT+DPO 三方做评测，采用 LLM-as-judge（裁判 DeepSeek-chat）：逐条多维打分 + 成对胜负（A/B 双向判定以抵消位置偏差）。**结论以测试集胜率为准，训练 loss 仅作收敛参考、不作质量证据。**

**SFT 收敛**
最终 train loss 收敛至约 0.3–0.5 区间，属健康收敛；未再出现旧版（泄漏数据）那种背诵式的 0.0x 低 loss。

### 成对胜负（核心指标）

| 对比 | template 桶胜率 | hard 桶胜率 | 解读 |
|------|----------------|------------|------|
| **SFT vs base** | **97%** | **77%** | 微调显著有效，且在非模板问法上同样取胜 → 具备真实泛化，不只是背模板 |
| **DPO vs SFT** | **29%** | **45%** | 两个桶均 < 50% → **当前合成偏好数据下，DPO 未带来提升，反而略有退步** |

### 逐条多维打分（1~5，均分）

| 模型 | 桶 | 正确性 | 有用性 | 语气 | 安全 | 总均分 |
|------|----|--------|--------|------|------|--------|
| base | template | 2.77 | 2.12 | 3.89 | 4.54 | 3.33 |
| **sft** | template | **3.75** | **3.61** | 4.39 | 4.64 | **4.10** |
| dpo | template | 3.52 | 3.38 | 4.33 | 4.50 | 3.93 |
| base | hard | 3.11 | 2.29 | 3.89 | 4.68 | 3.49 |
| **sft** | hard | **3.32** | **3.07** | 3.93 | 4.46 | **3.70** |
| dpo | hard | 2.89 | 2.71 | 4.00 | 4.39 | 3.50 |

**结论与据此做出的决策：**

- **SFT 是有效的、可交付的。** 相对 base，模板内胜率 97%、非模板 77%，逐维打分全面领先。这是本项目的主要成果。
- **DPO 在当前数据下是负优化，因此最终部署 SFT 版本。** 逐条数据定位了退步原因：DPO 后**正确性 / 有用性下降**（template 3.52/3.38 < SFT 3.75/3.61），而语气持平——即模型变得更"爱表演周到"（堆砌话术、甚至虚构"我有您的历史记录"这类系统能力），但实际解题能力变弱。安全维度也未受益（DPO 4.50 < SFT 4.64）：反幻觉 DPO 压住了"乱编订单号"，却引入了"虚构系统能力"这类新的不可靠行为，净效果未赚到。
- **为什么 DPO 没起效（归因）**：偏好数据为合成、rejected 是明显失败模式、规模仅 168 条，导致 DPO 学到的是表面风格差异而非真实质量差异。真正有效的偏好对齐需要**真实的好/坏回复对比**，这是合成数据的天花板。

## 模型精度说明（训练 vs 部署）

为避免「训练用 4bit、部署却是 FP16」的常见误解，这里把模型的精度生命周期讲清楚：

| 阶段 | 精度 | 说明 |
|------|------|------|
| 训练（QLoRA） | 基座 4bit（NF4） + adapter 高精度 | 4bit 仅为训练省显存的手段，基座冻结不更新 |
| 本仓库推理（serve.py） | 4bit | 直接以 4bit 加载，对应上方「推理性能」表 |
| 合并导出 merged_model | **FP16** | merge LoRA 时基座反量化回 16bit 再焊上 adapter；`model.safetensors` 约 2.9GB，与 1.5B×2字节≈3GB 吻合 |
| GGUF 导出（export_model.py） | 4bit（q4_k_m） | 内部经 FP16 中间态后量化落盘，供 llama.cpp / Ollama / LM Studio 本地部署 |
| 压测仓库部署 | FP16 | A/B 组加载 FP16 merged_model，C 组另行量化 4bit 作朴素基线 |

**要点：4bit 是训练阶段为塞进 8GB 显存的临时手段，不是模型的最终身份。** 合并后产出的是 FP16 权重（已实测约 2.9GB 验证）；下游部署用 4bit 还是 FP16，按各自的显存 / 延迟 / 精度约束分别决定，不必与训练一致。

> 量化方法辨析：训练用的 NF4（bitsandbytes）与 GGUF 导出用的 q4_k_m（llama.cpp）都叫「4bit」，但量化算法、分组方式、精度损失特性不同，分属训练生态与本地推理生态，不可混为一谈。

## 快速开始

```bash
# 安装依赖
pip install unsloth trl transformers datasets

# 1. 生成 SFT 数据（零泄漏 + 订单号条件性出现）
python data/data/prepare_data.py

# 2. 生成 DPO 偏好数据
python prepare_dpo_data.py
python add_antihallu_dpo.py        # 追加反幻觉定向偏好对

# 3. SFT 微调（每 epoch 存档）
python train_sft.py

# 4. DPO 对齐
python train_dpo.py

# 5. 诊断（贪心解码，验证行为是否真正改变）
python diagnose.py

# 6. 推理 + 性能测试
python serve.py
```

## 关键技术点

**为什么用 QLoRA（而非普通 LoRA / 全量微调）?**
全量微调 1.5B 需把 FP16 基座 + 全部参数的梯度和优化器状态放进显存（约 12GB），单张 8GB 卡放不下。QLoRA 叠加两件事省显存：① 基座以 4bit（NF4）加载并冻结，体积压到约 1/4；② 只训练占 1.18% 的 LoRA adapter（约 18.4M 参数）。两者叠加把训练显存压到约 1.6GB（相比全量约 12GB 降低约 87%），从而能在 RTX 4060Ti（8GB）上完成微调。代码中体现为 `FastLanguageModel.from_pretrained(..., load_in_4bit=True)`。

**为什么先 SFT 再 DPO?**
SFT 让模型掌握客服领域知识（学会回答），DPO 在此基础上优化回复质量与行为（学会更好地回答、回避不当行为）。跳过 SFT 直接 DPO，模型缺乏领域基础，对齐效果差。

**为什么幻觉订单号该用 DPO 而非继续调 SFT 数据比例?**
SFT 是「模仿」：把反例（无订单号 → 索要）混在正例里，比例从 8% 提到 34% 仍无法压住幻觉，因为信号被稀释。DPO 是「对比」：把同一问题的 chosen / rejected 摆在一起，梯度直接朝"远离编造订单号"推。本项目验证了 DPO 能精准消除这一**特定**失败模式；但也验证了它的代价——在合成偏好数据下会引入新的风格性副作用，整体质量未必提升（见「实验结果」）。两面都讲，才是对 DPO 适用边界的完整理解。

## 已知局限与改进方向

诚实标注当前版本的边界（多数已由评测量化）：

- **DPO 在当前数据下未带来提升**：测试集上 DPO-vs-SFT 胜率仅 29%（template）/ 45%（hard），且正确性、有用性较 SFT 下降。根因是偏好数据为合成、rejected 为明显失败模式、规模仅 168 条，DPO 学到的是表面风格而非真实质量差异。改进方向：用**真实的好/坏回复偏好对**重做 DPO；当前最终交付为 SFT 版本。
- **合成数据的泛化边界已被量化**：SFT 在 hard 桶（非模板探针）胜率 77%、均分 3.70，明显低于 template 桶的 97%、4.10——模型在模板内很强，出了模板就掉一截。残留模板串味（如"保修期"偶尔套用商品咨询模板、物流子场景混合）也属此列。根治需引入真实客服对话。
- **小模型 + 强约束下的"幻觉转移"**：定向 DPO 压住了"幻觉订单号"，却诱发了"虚构系统能力"（如声称掌握用户历史记录）这类新的不可靠行为——摁下一个、顶起一个，是 1.5B + 合成数据的典型表现。部署侧用低温/贪心解码 + system prompt 约束可缓解，根治仍需更优数据与更大模型。
- **评测自身的局限**：hard 集 28 条偏小且由人工构造；LLM-as-judge 与人工标注存在偏差，条件允许时应抽样做人工复核校准。
